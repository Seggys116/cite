# Connector API

JSON over HTTP, prefix `/api/v1`. Every route except `POST /auth/login` and `GET /healthz` needs `Authorization: Bearer <token>`, where the token is a session token from login or a long-lived API token. Requests from addresses outside the allowlist get a bare connection close.

Errors are `{"error":"message"}` with a matching status code. Bodies are capped at 1 MiB, and at 128 KiB on the certificate routes.

## Sites

| Route | Body | Response |
|---|---|---|
| `GET /sites` | none | `[Site]` |
| `POST /sites` | `Site` without `history`, plus an optional `github_token` | `Site` |
| `GET /sites/{id}` | none | `Site` plus `live:{blue:[{addr,status}],green:[...]}` |
| `PUT /sites/{id}` | `Site` | `Site` |
| `DELETE /sites/{id}?purge_volumes=true` | none | `{ok:true}`. Without `purge_volumes=true` the site's persistent volumes are kept. |
| `GET /sites/{id}/volumes` | none | `[{name,mount_path,size_bytes,mounted,created_at,declared}]`: declared volumes in order, then leftovers (`declared: false`, `mount_path: ""`). `size_bytes` and `created_at` are `null` when Docker does not report them or the volume is not created yet; `mounted` is true when a running executor mounts it. |
| `DELETE /sites/{id}/volumes/{name}` | none | `{ok:true}` after deleting the volume's data. 409 while the volume is declared and the site has a running container, or while a running slot mounts it; 404 when no such volume exists. |
| `GET /sites/{id}/zone-secret` | none | `{configured,readable,header:"X-Cite-Origin-Secret",created_at,fingerprint}`; never the secret. `readable` is false when `zone-secrets.json` could not be read at start, in which case `configured: false` means "unknown". `fingerprint` is the first 8 hex digits of its SHA-256, `null` when none is stored. |
| `POST /sites/{id}/zone-secret` | none | Creates or replaces the secret and returns `{secret,header,created_at,fingerprint}` once, with `Cache-Control: no-store`. 404 for an unknown site, 400 unless the site has `access.zone_lock` (checked again once the change lock is held). 503 when HAProxy is not running or does not confirm the new secret: the old secret is kept and the rotation is audited as `zone_secret.rollback`, or `zone_secret.rollback_failed` / `zone_secret.rollback_unconfirmed` (with `the rollback FAILED` in the error) when the undo fails; rotate again after that. |
| `POST /sites/{id}/deploy` | `{targets:[Target],note?}` | `Deployment` |
| `POST /sites/{id}/switch` | `{slot}` | `Deployment` |
| `POST /sites/{id}/rollback` | none | `Deployment` |
| `POST /sites/{id}/maintenance` | `{enabled,page_id?}` | `Site` |

A site with `access.zone_lock` gets a 43-character secret generated by the node when the site is saved; it lives in `zone-secrets.json`, is injected into the rendered HAProxy config as a firewall rule and is never part of `edge.json`, the firewall rule list, an audit entry or `GET /haproxy/config`. Rotating applies the change with rollback, and the old value stops working once HAProxy has reloaded. Turning the lock off or deleting the site deletes the secret. The rotation is audited as `zone_secret.rotate` with the fingerprint only.

`github_token` is used for a site with a `source`, which needs the orchestrator. It is optional when the connector has `CITE_GITHUB_TOKEN` (or `CITE_GITHUB_TOKEN_FILE`) set, in which case a given token overrides it for that site; with neither the request is refused with 400. A per-site token is stored in `secrets.json`, never in the site, and never returned; the node token is never stored. `GET /node` reports `github: {token_configured, source}`. See [Orchestrator](orchestrator.md#github-token).

`PUT /sites/{id}` changes the name, hosts, `path_regex`, kind, health check and source. The active slot, both slots' targets and the maintenance flag are kept from the stored site, whatever the body says, so a stale copy of a site cannot undo a deploy. Those fields change only through `deploy`, `switch`, `rollback` and `maintenance`. `DELETE /sites/{id}` returns 409 naming the firewall rules while any rule is scoped to the site; delete or change those rules first.

Deploys, switches, rollbacks, site changes and every other change that touches the HAProxy config run to completion on the node even if the client disconnects or the 700 s request limit passes. Read the result afterwards from `GET /sites/{id}`. A change is refused, and the stored config restored, when a reachable HAProxy rejects the rendered config (400) or does not load it (400 for a refused reload, 503 for an unconfirmed one). When HAProxy cannot be reached at all an ordinary change is stored and applied on the next reload, audited as `config.pending`; a change that adds or alters a protection is not (see below).

Protection changes need a running HAProxy that confirms it loaded them: turning on or changing a site's `access.cloudflare_only`, `access.zone_lock` or `access.bots`, changing `settings.cloudflare_ranges`, and adding or editing an enabled blocking rule (one with an `action`) or a rule with a `secret` header matcher. Without that confirmation the change is rolled back and answered with 503 (`haproxy must be running to apply this protection change`), or 400 when a running HAProxy refuses the config. Removing a protection keeps the tolerant behaviour.

Every site, firewall, page and settings change uses the same sequence: validate and dry-render, store, apply, and on failure restore the previous configuration and load it again. The restore is audited as `config.rollback`. When the undo itself fails the error says `the rollback FAILED` and the audit entry is `config.rollback_failed` (the stored configuration could not be written back) or `config.rollback_unconfirmed` (it was written back but HAProxy did not confirm loading it); check `GET /node` and reload when that happens. `POST /haproxy/reload` also runs to completion if the client disconnects.

`POST /haproxy/reload` always asks HAProxy to reload, even when the config is unchanged, so renewed certificates are picked up and a failed reload can be retried. It returns 503 when HAProxy is unreachable or does not confirm a new worker.

`switch` and `rollback` start a stopped slot again on the git ref it last ran, not on the site's current branch.

`Site.volumes` (`[{name,mount_path}]`, left out of the JSON while empty) and `Site.outbound` (default `true`, always returned) are part of the site body and change through `PUT /sites/{id}` like other build settings: the change is stored without a HAProxy reload and takes effect on the next deploy, with the site status reporting the settings as not current meanwhile. Volumes need a server runtime; a static site with volumes is refused with 400. Rules are in [Orchestrator](orchestrator.md#persistent-volumes). Deleting volume data is audited as `site.volume.delete` and a purging site delete as `site.volumes.purge`, with ids only. A node with the orchestrator lists the capabilities `volumes` and `outbound`.

`Site.outbound_rules` (`{mode,allow,deny,block_mail}`, left out of the JSON while it is the default `{mode:"public",allow:[],deny:[],block_mail:true}`) sets where an outbound site may connect when the node's egress mode is `filtered`. `mode` is `public` (the public internet plus private destinations in `allow`) or `allowlist` (only destinations in `allow`, which must then hold at least one entry). `allow` and `deny` each hold at most 64 distinct entries, each an IP, a CIDR, or a lowercase host name of `a-z0-9.-_` up to 253 characters; a leading `.` or `*.` makes a name cover its subdomains and is stored as a leading `.`. `deny` always wins over `allow`, the node's `CITE_STACK_EGRESS_DENY_*` lists win over both, and loopback, link-local and metadata addresses open only through an explicit CIDR. `block_mail` (default `true`) refuses ports 25, 465 and 587. `POST /sites` and `PUT /sites/{id}` validate the rules strictly and answer 400 with the reason; a stored config is loaded without judging them, and a deploy checks them again. A change takes effect on the next deploy, which recreates the site's egress proxy; see [Hardening](hardening.md#per-site-outbound-rules).

`deploy` writes the targets into the idle slot, waits for every target to pass health checks (up to 60 s, or the build wait of 600 s by default for a site built from a repo), flips the active slot through the HAProxy runtime API, and records a `Deployment`. A failed health check leaves the active slot untouched and records `failed`.

## Doppler

A site built from a repository can take build and runtime variables from a Doppler project and config. How syncing, merging and redeploys work is in [Running a node](node.md#doppler). A node with the orchestrator lists the capability `doppler`.

| Route | Body | Response |
|---|---|---|
| `GET /doppler/projects` | none | `[{slug,name}]` the node token can see |
| `GET /doppler/projects/{project}/configs` | none | `[{name,environment}]` |
| `GET /sites/{id}/doppler` | none | `DopplerBinding` |
| `PUT /sites/{id}/doppler` | `{project,config,build,runtime,token?}` | `DopplerBinding` after the first sync |
| `DELETE /sites/{id}/doppler` | none | `DopplerBinding` (unbound) |
| `POST /sites/{id}/doppler/sync` | none | `DopplerBinding` after the sync |

`DopplerBinding` is `{bound,project,config,build,runtime,token_source,status,last_sync_at,last_error,keys,redeploy_needed,pending_redeploy,skipped:[{name,reason}]}`. `token_source` is `site`, `node` or `none`; `status` is `synced`, `syncing`, `error` or `idle` (unbound, or not synced since the connector started); `keys` counts the distinct synced names. `last_error` holds the last sync error, otherwise a note naming the skipped variables or saying the synced values wait for a deploy. Values and tokens are never returned.

`project` and `config` are 1 to 100 characters from letters, digits, `.`, `_` and `-`, or both empty to bind through a service token alone: then the site needs a token starting with `dp.st.`, sent in this request or already stored for the site (the node token is not enough), the secrets download names no project or config, and `project` and `config` read `null` in `DopplerBinding`. Setting only one of them is refused. At least one of `build` and `runtime` must be true; `token` is 1 to 512 printable ASCII characters. Unknown fields are refused and the body is capped at 4 KiB (413 above). The routes answer 400 for a site without a `source`, 404 for an unknown site, and 400 with "No Doppler token: set CITE_DOPPLER_TOKEN on the connector or pass a token for this site" when no token is available. The project routes use the node token only.

`PUT` stores the binding through the normal site update path (with the strict source validation), stores the optional token as the site's own, then syncs once. When that sync fails the error is returned (400 for a rejected token or an unknown project or config, 429 when Doppler rate limits, 503 when it cannot be reached) and the previous binding, token and synced values are put back. A successful bind redeploys the site. `DELETE` removes the binding, the site's Doppler token and the synced values, keeps the manual variables and does not redeploy; the answer has `redeploy_needed: true` while the running site still holds Doppler values. `POST /sites/{id}/doppler/sync` is 400 for an unbound site; it redeploys only when the values changed.

Binding, restoring and removing are audited as `site.doppler.bind` (site, project, config and the two flags), `site.doppler.restore` and `site.doppler.unbind`; a new site token as `site.doppler.token.set`; a requested sync as `site.doppler.sync.request`; and a sync that changed the values as `site.doppler.sync` with the counts. No entry holds a value or a token.

## Firewall

| Route | Response |
|---|---|
| `GET /firewall/rules` | `[FirewallRule]` |
| `POST /firewall/rules` | `FirewallRule` |
| `PUT /firewall/rules/{id}` | `FirewallRule` |
| `DELETE /firewall/rules/{id}` | `{ok:true}` |
| (rules) | | A header matcher with `secret: true` is write-only: `equals` and `regex` come back as an empty string in every response. A `PUT` (or `POST` of an existing id) that leaves the value empty keeps the stored value of the header with the same name; with nothing stored it is a 400. Matchers are lists (values of one field are OR'd, fields are AND'd); the singular names of earlier releases are still accepted. Rules also carry `redirect`, `headers`, `cors`, `label`, the `scheme` matcher and an optional `action`; see [Firewall](firewall.md). |
| `POST /firewall/bulk` | `{created,replaced,deleted,ignored,rules:{created:[FirewallRule],replaced:[FirewallRule]}}` |
| `GET /firewall/presets` | `[{name,title,description,rules:[FirewallRule]}]` |
| `POST /firewall/presets/{name}/apply` | `[FirewallRule]` added; a rule that already has a preset's id is refreshed to the current definition, keeping its `enabled` flag and site scope |

`POST /firewall/bulk` takes `{"replace": [FirewallRule], "delete": [id]}` (both optional, at least one non-empty, at most 200 rules each, body at most 512 KiB; larger bodies get 413) and applies it as one change: every rule is validated, the resulting configuration is validated as a whole (including redirect loops across rows), rendered once, applied once and rolled back as a whole if HAProxy does not take it. Nothing changes unless everything is valid; a bad rule gives a 400 naming its id. A rule in `replace` is created when its id is new and replaces the stored rule otherwise; secret header values follow the single-rule semantics, matched per rule by header name (repeated names pair up in order), so a blank secret keeps the stored value and with nothing stored is a 400 naming the rule and header. An id in both lists, or twice in one list, is a 400; a `delete` id that does not exist is ignored and counted in `ignored`. The returned rules are redacted. One `firewall.bulk` audit entry records the counts and the rule ids (clipped to the audit detail limit), never rule bodies. Whether HAProxy must be running follows the same rule as for single rule changes.

## Certificates

TLS certificates for the node's HTTPS listener. How HAProxy uses them is in [Running a node](node.md#certificates).

| Route | Body | Response |
|---|---|---|
| `GET /certificates` | none | `{items:[Cert],https_port,https_effective_port,automatic,dir_ready,uncovered_hosts}` |
| `GET /certificates/{id}` | none | `Cert` (an automatic one has the id `auto:<site id>`) |
| `POST /certificates` | `{name,certificate,private_key}` | 201 `Cert` plus `warning` when HTTPS is off |
| `PUT /certificates/{id}` | `{name?,certificate,private_key}` | `Cert` plus `warning` when HTTPS is off |
| `DELETE /certificates/{id}` | none | 204 |

`certificate` is a PEM chain of 1 to 10 `CERTIFICATE` blocks, leaf first. `private_key` is one unencrypted `PRIVATE KEY` (PKCS#8), `EC PRIVATE KEY` or `RSA PRIVATE KEY` block. `name` is 1 to 64 characters from letters, digits, space, `.`, `_` and `-`, starting with a letter or digit and not ending with a space. `PUT` replaces or renews the certificate in place under the same id and keeps `created_at`; leave `name` out to keep the current name. Unknown fields are refused.

```json
{
  "id": "01JD3Z8Q5V7M2K4N6P8R0T1W3Y",
  "name": "shop",
  "subject": "CN=shop.example.com",
  "sans": ["shop.example.com", "*.example.net"],
  "issuer": "CN=Example CA",
  "not_before": "2026-11-05T00:00:00Z",
  "not_after": "2027-02-03T00:00:00Z",
  "days_left": 88,
  "fingerprint_sha256": "9f2c...",
  "key_type": "ecdsa-p256",
  "created_at": "2026-11-06T09:30:00Z",
  "covers": ["shop.example.com"],
  "uncovered_hosts": ["blog.example.com"]
}
```

`key_type` is `rsa-2048`, `rsa-3072`, `rsa-4096`, `ecdsa-p256`, `ecdsa-p384`, `ed25519`, or another `rsa-<bits>`, `ecdsa-p521` or `oid:<oid>` value. `days_left` goes negative once a stored certificate has expired. `covers` lists the configured site hosts that one of the certificate's names matches, either exactly or through a single-label wildcard (`*.example.com` matches `www.example.com`, not `example.com` or `a.b.example.com`). `source` is `api` for uploaded certificates and `manual` for files placed in the directory by hand; manual entries have the id `file:<name>`, are read-only (get, replace and delete answer 404) and are only listed when they parse. An uploaded file that cannot be read is listed with a `warning` string, empty dates and `key_type` `unknown`, and can be replaced or deleted by id. `uncovered_hosts` on a certificate lists the site hosts it does not cover; on the list response it lists the site hosts that no stored certificate covers. `https_port` is the node's setting and `dir_ready` is whether the certificate directory exists and the connector can write to it. The private key is never returned by any route.

Checks, each failing with 400 and a message that names the problem: the body is JSON with only the listed fields; the name rules above; the PEM holds only the allowed block types and counts; the key is not encrypted and is RSA of at least 2048 bits, ECDSA P-256 or P-384, or Ed25519; the key matches the leaf; the leaf is not expired and does not start more than 24 hours from now; there are fewer than 64 uploaded certificate files (unreadable ones count). A leaf already stored or hand-placed, even under another name, is 409. An unknown or malformed id is 404. A body over 128 KiB is 413. The 128 KiB limit is on the whole JSON body; clients should check 100 KiB of combined PEM before sending. The name must also start with a letter or digit and not contain five dashes in a row. Key parse errors never quote the key.

Every change is applied before it is acknowledged: the connector writes the file, renders the config, runs `haproxy -c` on it and reloads HAProxy. If HAProxy rejects the config (400) or does not load it (503) the file is put back as it was and the error says the change was rolled back. When HAProxy cannot be reached at all the change is kept and applied on the next reload, as for any other config change; the response then carries a `warning` and the audit entry ends in `haproxy=unreachable`.

When `settings.https_port` is unset and no site has `access.cloudflare_only` or `access.tls: "flexible"`, the upload succeeds and the response carries a `warning`: the certificate is stored but nothing serves it. The connector does not change settings on its own; set the port with `PUT /settings`. When such a site exists the node binds 443 itself (`https_effective_port`) and keeps an automatic self-signed certificate (`source: "auto"`, `warning` explaining it) for each site's hosts that no other certificate covers. Those entries are read-only: `PUT` and `DELETE` on an `auto:` id answer 400 "automatic certificates are managed by the node", they are not counted in the 64 certificate limit, and `uncovered_hosts` ignores them. See [Automatic certificates and Cloudflare](node.md#automatic-certificates-and-cloudflare).

A certificate the node issued itself through Cloudflare's Origin CA or Let's Encrypt also carries `managed` (`"origin-ca"` or `"acme"`) and `renew_at` (when the node renews it). Replacing it with an upload through `PUT` makes it an ordinary uploaded certificate again: `managed` disappears and the node no longer renews it.

### Issuing certificates

The node can make the certificate itself instead of receiving one. Every route ends in the same store path as an upload: the certificate and the key the node generated are checked like an upload, written as one `<id>.pem` file, `haproxy -c` runs and HAProxy reloads, with the same rollback, the same 64 certificate limit and the same `Cert` response. The result has `source: "api"` and a normal id, so it can be replaced and deleted like any other. Keys are ECDSA P-256, generated on the node, and never leave it or appear in a response, log or audit entry.

| Route | Body | Response |
|---|---|---|
| `POST /certificates/generate` | `{hosts,name?,days?}` | 201 `Cert` with `warning` |
| `POST /certificates/origin-ca` | `{hosts,name?,cloudflare_token,validity_days?,remember_token?}` | 201 `Cert` with `warning` |
| `POST /certificates/acme` | `{hosts,email,cloudflare_token,agree_tos,name?,staging?}` | 202 `{job_id,status,staging,note}` |
| `GET /certificates/acme` | none | `{jobs:[Job],certificates:[Managed],token_stored}` (`token_stored` is true when any token, per certificate or legacy, is stored) |
| `GET /certificates/acme/{job_id}` | none | `Job` |

`hosts` lists 1 to 32 hostnames or `*.` wildcards with the same rules as site hosts (letters, digits and `-`, labels of at most 63 characters, at most 253 in all); they are lowercased and duplicates dropped. A wildcard needs at least two labels under it (`*.example.com`, not `*.com`). `name` follows the upload name rules; without it the name is built from the first host, for example `letsencrypt shop.example.com`. Bodies are capped at 16 KiB (413 above that) and unknown fields are refused.

- `generate` signs a self-signed certificate on the node. `hosts` may also hold IP addresses and single-label names here. `days` is 1 to 3650 (default 825). The `warning` starts with "Self-signed: browsers do not trust it; fine behind Cloudflare Full (not strict)."
- `origin-ca` sends a signing request for the node's new key to Cloudflare's Origin CA (`POST https://api.cloudflare.com/client/v4/certificates`, `request_type` `origin-ecc`) and stores the certificate it returns. `validity_days` is one of 7, 30, 90, 365, 730, 1095 or 5475 (default 5475). `cloudflare_token` is an API token with the permission Zone, SSL and Certificates, Edit, sent as `Authorization: Bearer`; a legacy Origin CA key (it starts with `v1.0-`) is sent as `X-Auth-User-Service-Key` instead. The token is used for this request only unless `remember_token` is true; then it is stored on the node and used for renewals. The `warning` says which happened. Cloudflare's own error message is passed on with any copy of the token replaced by `[redacted]`; a rejected token is 400.
- `acme` orders a Let's Encrypt certificate (`staging: true` uses the staging CA, whose certificates browsers do not trust) and proves each name with a DNS-01 challenge through the Cloudflare DNS API. `agree_tos` must be `true` (it accepts the Let's Encrypt Subscriber Agreement) and `email` is the account contact. IP addresses are refused; wildcards work because the challenge is DNS-01. The token needs Zone, Zone, Read and Zone, DNS, Edit on every zone the hosts belong to. For each name the node finds the zone (`GET /zones?name=`, most specific first), creates the `_acme-challenge` TXT record, polls the Cloudflare API until the record is listed, then asks Let's Encrypt to validate. The TXT records are deleted afterwards whether the order succeeds or fails. This takes up to a few minutes, so the route answers 202 with a `job_id` at once and the work continues in the background; poll `GET /certificates/acme/{job_id}`.

**The ACME route stores the Cloudflare token.** Renewing a Let's Encrypt certificate needs a new DNS challenge, so when the certificate is issued the token is saved on the node as the secret `cloudflare-token:<certificate id>` in `secrets.json` (mode 0600, the same file as the GitHub tokens). The 202 `note` says so. Every certificate keeps its own token, so issuing another certificate with a differently scoped token never overwrites the first one's. Only names are ever reported (`token_stored`); the value is never returned, logged, put in an audit entry or shown in an error. Origin CA certificates are renewed with their own stored token, which is why `remember_token` matters there. Certificates marked as managed before tokens were kept per certificate renew with the old single secret `cloudflare-token` until they are issued again. Deleting a certificate, or replacing it by hand, removes its token.

`Job` is `{id,kind,hosts,status,error?,staging,certificate_id?,not_after?,renew_at?,created_at,finished_at?}`. `kind` is `acme` for an order and `renew` for a renewal; `status` is `pending`, `issued` or `failed`. `error` explains a failure in plain text. The node keeps the last 50 jobs in memory; they are gone after a restart, the certificates are not. `Managed` is `{id,name,kind,hosts,status,not_after,renew_at,staging,error?,next_attempt?}` for every stored certificate with a `managed` marker (`kind` `acme` or `origin-ca`), where `error` and `next_attempt` describe the last failed renewal.

The ACME account key is ECDSA P-256, made on first use and kept in `acme-account.pem` in the data directory (mode 0600). It is reused for every later order and renewal.

**Renewal.** A background task checks once an hour (first one minute after start) and renews each managed certificate 30 days before it expires, or at two thirds of its lifetime when it is shorter than 90 days. A renewal issues a new certificate for the same names, from the same issuer (and the same CA environment for ACME), and swaps it in under the same id and name through the replace path, so HAProxy reloads with rollback and the change is audited as `certificates.renew` by `system`. A failed renewal is audited as `certificates.renew_failed`, listed as a failed `renew` job and retried after one hour, then two, four and so on up to once a day. Without a stored token the renewal fails with an error saying so.

**Limits.** At most one Origin CA or ACME operation runs at a time on a node, and at most 10 start per hour; anything beyond answers 429 (the hourly limit also sets `retry_after` and the `Retry-After` header). Renewals wait for a running operation and do not count toward the hourly limit. `generate` is local and not limited.

**Outbound requests.** The node only connects to `https://api.cloudflare.com` and the two Let's Encrypt ACME hosts (`acme-v02.api.letsencrypt.org`, `acme-staging-v02.api.letsencrypt.org`). Every URL, including the ones an ACME server hands back, is checked against that list before a connection opens; redirects are not followed; each request times out after 20 seconds and a response larger than 1 MiB is refused.

The issuing routes are audited as `certificates.generate`, `certificates.origin_ca` and `certificates.acme` (same detail as `certificates.create`), a failed order as `certificates.acme_failed` with the job id and the error, and storing the token as `certificates.token_stored` with the secret name only.

`create`, `replace` and `delete` are audited as `certificates.create`, `certificates.replace` and `certificates.delete` with the id, name, SHA-256 fingerprint and subject. A change that had to be rolled back adds `certificates.rollback` with the id. When the undo itself could not be written the entry is `certificates.rollback_failed`, and when the undo was written but HAProxy did not confirm loading it again the entry is `certificates.rollback_unconfirmed`. Rotating a zone secret is audited as `zone_secret.rotate` (site and fingerprint, never the secret) with the same three rollback outcomes as `zone_secret.rollback`, `zone_secret.rollback_failed` and `zone_secret.rollback_unconfirmed`. Firewall and site changes that were rolled back are audited as `config.rollback`, `config.rollback_failed` or `config.rollback_unconfirmed`, and a change saved while HAProxy could not be reached is `config.pending`. Start-up writes `config.migrated` when it rewrote `edge.json` (see the upgrade section in node.md).

## Alerts

The node watches its sites and can send a message to webhooks (Discord, Slack or a generic JSON endpoint) and to one SMTP account.

| Route | Body | Response |
|---|---|---|
| `GET /alerts` | none | `AlertSettings` with secrets masked |
| `PUT /alerts` | `AlertSettings` | the stored settings, masked |
| `POST /alerts/test` | `{target}` where target is a webhook id or `email` | `{ok}` or `{ok:false,error}`; 404 for an unknown target |

```json
{
  "enabled": true,
  "cooldown_secs": 900,
  "webhooks": [
    {"id": "ops", "name": "Ops channel", "kind": "slack", "url": "https://hooks.slack.com/...", "events": ["site_unhealthy", "build_failed"]}
  ],
  "email": {
    "host": "smtp.example.com", "port": 587, "tls": "starttls", "username": "alerts",
    "password_set": true, "from": "alerts@example.com", "to": ["ops@example.com"], "events": []
  }
}
```

`kind` is `generic`, `discord` or `slack`. `events` is any of `site_unhealthy`, `site_recovered`, `build_failed`, `deploy_succeeded`, `cert_expiring` and `node_error`; an empty list means all of them. `tls` is `starttls` (default, port 587), `tls` (implicit TLS, usually port 465) or `none`; `none` cannot be combined with a username, so credentials never travel in the clear. `cooldown_secs` (default 900, at most 7 days) is the minimum gap between two messages for the same site and event. At most 10 webhooks and 5 recipients; ids are 1 to 32 characters from `a-z`, `0-9` and `-` (and not `email`); names are 1 to 64 characters. The body is limited to 16 KiB, and unknown fields are ignored.

Secrets are write-only. Webhook URLs are returned as `https://host/...` and the SMTP password is never returned, only `password_set`. On `PUT`, a webhook whose `url` is blank or equal to the masked value keeps the URL stored for the same `id`, and a blank `password` keeps the stored one only while `host`, `port`, `tls` and `username` are unchanged (otherwise the `PUT` is refused and the password must be entered again, so a stored password is never sent to another server); a webhook with a new id needs a URL. Removing `email` deletes the stored password. Setting `username` to blank also clears the password. The settings live in `alerts.json` in the data directory (mode 0600). If that file cannot be read at start, alerts stay off, the file is left untouched and `PUT` answers 500 until it is fixed.

A webhook URL must be `https://`, have no credentials and name a public host. Every send resolves the name, refuses the message if any answer is a private, loopback, link-local, carrier-grade NAT, multicast or otherwise reserved address (this includes the cloud metadata address), connects to the one address it checked, and does not follow redirects or use proxies. The same check applies to the SMTP host, so a mail relay on a private network cannot be used; point the node at a relay with a public address. Test sends and real sends share these rules.

What is watched, every 30 seconds: a site must look unhealthy (or healthy again) on two checks in a row before `site_unhealthy` or `site_recovered` is sent, and a running deploy never counts as unhealthy; `build_failed` is sent when a new failed build appears and `deploy_succeeded` when a new promotion appears (history that already exists when the node starts, or when alerts are switched on, is not announced); `cert_expiring` is sent for an uploaded certificate with 14 days or fewer left, at most once per 24 hours per certificate; `node_error` is sent once when the node cannot read site status for three checks in a row. Deliveries run in the background, at most four at a time, and are retried twice with a growing delay on connection errors, timeouts, 429 and 5xx answers. Failures are logged by target id without the URL or any secret. Webhook bodies: Slack `{"text"}`, Discord `{"content"}` (cut to 1900 characters), generic `{"event","site","message","detail","at"}`. Email is plain text, base64 encoded.

`PUT` is audited as `alerts.update` (whether alerts are enabled, the webhook ids and whether email is set) and a test as `alerts.test` (the target id and the result); neither entry holds a URL, a host or a password.

## Analytics

`summary`, `timeseries`, `bots`, `top`, `requests`, `facets` and `compare` take one shared filter: a time range (`window` of `15m`, `1h`, `24h`, `7d` or `30d`, default `1h`, or `from` and `to`) plus any of the filters in the table below. Every route needs the bearer token, and a session token and an API token are both accepted. Storage, retention, bot scoring and the export format are described in [Analytics](analytics.md). A node that has these filters lists the capability `analytics-filters`.

| Route | Response |
|---|---|
| `GET /analytics/summary` | `{requests,bytes_in,bytes_out,blocked,errors_4xx,errors_5xx,avg_ms,p50_ms,p95_ms,p99_ms,status:{"2xx":n,...},methods:{GET:n},content_types:{...},sizes:[{le,count}],top_paths:[{key,count,bytes}],top_ips:[...],top_user_agents:[...],top_hosts:[...],top_blocked:[...]}` plus the fields in "Filter echo" below |
| `GET /analytics/timeseries` | `{step_secs,points:[{ts,requests,bytes_out,errors,blocked,avg_ms}]}` plus the echo. `ts` is in seconds. With only a window and one site the step is 60 seconds up to 48 hours and 3600 beyond; any other query picks 1, 5 or 15 minutes, or 1, 6 or 24 hours, so a chart has at most about 360 points. |
| `GET /analytics/requests?limit=&offset=&before_ts=&before_id=&envelope=` and the filter | `[LogEvent]` newest first, `limit` 1 to 1000 (default 100). The original names `status`, `method`, `path` (substring of the path), `ip`, `blocked` and `site` still work. Without `envelope=true` the answer is the bare array and `window` is ignored, as before; with it the answer is `{items,next_cursor:{before_ts,before_id}\|null,partial,scanned?,filters,from_ms?,to_ms?}`. `offset` is at most 100000; `before_ts` and `before_id` (both, from `next_cursor`) return rows strictly older and cannot be combined with `offset`. |
| `GET /analytics/bots` | `{total_requests,bot_requests,bot_share_pct,classes:[{key,count,bytes}],signals:[...],agents:[...],score_buckets:[...]}` plus the echo. `classes` keys are `human`, `suspect`, `crawler`, `tool`, `bot`; `score_buckets` keys are `0-19`, `20-39`, `40-59`, `60-79`, `80-100`. |
| `GET /analytics/top?kind=&sort=&limit=` and the filter | `{items:[{key,count,bytes}]}` plus the echo. `kind` is required: `paths`, `hosts`, `referers`, `agents`, `content_types`, `statuses`, `ips` or `languages`. `sort` is `count` (default) or `bytes`. `limit` 1 to 1000 (default 100). An unknown `kind` or `sort` is a 400. |
| `GET /analytics/facets` | `{site,host,method,status_class,bot_class}`, each `[{key,count}]` with at most 50 values, biggest first, plus the echo. The counts respect every filter given, so a client can fill its pickers from the same query it charts. |
| `GET /analytics/compare?against=previous` and the filter | `{against:"previous",current:Summary,previous:Summary,delta:{requests,bytes_in,bytes_out,blocked,errors_4xx,errors_5xx,avg_ms,p50_ms,p95_ms,p99_ms}}`. Each summary carries the echo; `previous` covers the range of equal length that ends where `current` starts (`from_ms` and `to_ms` say exactly which). Each delta is `{current,previous,abs,pct?}`, and `pct` is absent when the previous value was 0. |

**Filter.** Parameters are ANDed. A list takes a comma list or a repeated parameter. An unknown parameter, a bad value or a repeated single-value parameter is a 400 that names the parameter. An empty value counts as not given (except `window` and `status`, which are 400s as before).

| Parameter | Values |
|---|---|
| `window` | `15m`, `1h`, `24h`, `7d`, `30d`. Exclusive with `from` and `to`. |
| `from`, `to` | Milliseconds since the epoch or RFC 3339, `from` inclusive and `to` exclusive. `to` defaults to now; `to` needs `from`; `from` must be earlier; at most 400 days. |
| `site` | Up to 20 site ids. |
| `host`, `path_prefix`, `path_exact` | Exact host (255 bytes), path prefix and exact path (2048 bytes). |
| `method` | List of method tokens, case-insensitive. |
| `status`, `status_min`, `status_max` | One status code, or an inclusive range, 100 to 599. |
| `status_class` | List of `1xx` to `5xx`. |
| `blocked` | `true` (blocked by any rule), `unblocked`, `rule:<id>` (one rule), or `false`, which is accepted and does not filter. |
| `bot_class` | List of `human`, `suspect`, `crawler`, `tool`, `bot`. |
| `min_bot_score`, `max_bot_score` | 0 to 100. |
| `client_ip` | An address or a network such as `10.0.0.0/8` or `2001:db8::/32`. |
| `user_agent`, `referer` | Case-insensitive substring, 3 to 64 characters; `%` and `_` match themselves. |
| `min_duration_ms` | Total time of at least this many milliseconds. |
| `content_type` | Case-insensitive prefix of the response content type, 2 to 64 characters. |

There is no `country` filter because the node does not record one; it is a 400 like any unknown name.

**Filter echo.** Every answer except the bare request list adds `filters` (the filter as applied, with lists as arrays and a network in its masked form), `partial`, `scanned` (raw rows examined; absent when rollups answered), `from_ms` and `to_ms` (the range actually used; rollup answers cover whole minutes or hours, so they can be wider than asked), and `source` (`rollup_minute`, `rollup_hour` or `raw`). A query with only a time range and at most one site is answered from the rollups. Anything else reads raw rows, examines at most 5,000,000 of them newest first, and reports `partial: true` with the cut `from_ms` when the range held more; for the request list, `next_cursor` then resumes below that cut.
| `GET /analytics/stats` | `{rows,db_bytes,oldest_ts_ms,newest_ts_ms,write_batches,write_errors,retention_days,archive_before_delete,max_bytes,ingest_stalls}`. The two timestamps are `null` for an empty database, and `max_bytes` is `null` when no size cap is set. `retention_days` 0 means rows are kept forever. `ingest_stalls` counts the times the log receiver waited on the database writer. |
| `GET /analytics/archives` | `{items:[{name,kind,bytes,created_ms,sha256,rows,from_ms,to_ms}],dir_bytes}`, newest first. `kind` is `archive` or `backup`; `from_ms` and `to_ms` are the oldest and newest request in the file, `null` for an empty backup. `dir_bytes` is everything in the archive directory. |
| `POST /analytics/backup` | No body. Writes a consistent copy of the database and returns its item. |
| `POST /analytics/cut` | `{before_ms \| before_days, archive?, dry_run?}` returns `{dry_run,cutoff_ms,rows,oldest_ms,archived_rows,files,archive}`. See below. |
| `POST /analytics/restore` | `{name, again?}` imports an archive and returns `{rows}`. A backup name is a 400. An archive that was already restored is a 409 unless `again` is `true`, which imports it a second time and duplicates its rows. A failed restore can be partially applied and leaves no marker. |
| `GET /analytics/archives/{name}` | The file, `application/gzip` or `application/vnd.sqlite3`, with `X-Archive-Sha256`. |
| `DELETE /analytics/archives/{name}` | `{ok:true}`; removes the file and its manifest entry. |
| `GET /analytics/export?kind=&top=&format=&from=&to=&site=&status_min=&status_max=&bot_class=&min_bot_score=&host=&path_prefix=&client_ip=&method=&limit=` | A streamed file download, not JSON. See below. |

### Export

| Parameter | Values |
|---|---|
| `kind` | `requests` (default), `hourly`, `bots`, `top` |
| `top` | Required with `kind=top`, rejected otherwise; the same names as `/analytics/top` |
| `format` | `csv` (default), `ndjson` |
| `from`, `to` | Milliseconds since the epoch or RFC 3339. `from` inclusive, `to` exclusive, `from` must be earlier |
| `site` | A site id |
| `status_min`, `status_max` | 100 to 599, inclusive; `status_min` must not exceed `status_max` |
| `bot_class` | `human`, `suspect`, `crawler`, `tool`, `bot` |
| `min_bot_score` | 0 to 100 |
| `host`, `path_prefix`, `client_ip`, `method` | Exact host (255 bytes at most), path prefix (1024 bytes at most), IP address, HTTP method token |
| `limit` | 1 to 1,000,000; default 1,000,000 |

The response is 200 with `Content-Type: text/csv; charset=utf-8` or `application/x-ndjson`, `Content-Disposition: attachment; filename="cite-<kind>-<site|all>-<UTC date>.<csv|ndjson>"`, `X-Content-Type-Options: nosniff` and `Cache-Control: no-store`. A bad parameter is a 400 `{error}` naming it. A third simultaneous export on one node is a 429. A failure after the download has started cannot change the status, so the connection is aborted instead of ending the body normally. Each export is recorded in the audit log as `analytics.export` with the kind, format and filters.

```sh
curl -H "Authorization: Bearer $TOKEN" -OJ \
  "https://node:7443/api/v1/analytics/export?kind=requests&bot_class=crawler&from=2026-11-01T00:00:00Z"
```

### Archives, backups and cuts

The archive directory is `CITE_ANALYTICS_ARCHIVE_DIR` (default `<data>/analytics/archive`). Names are those returned by the list; anything with a path separator, `..`, other characters or an unknown prefix or extension is a 400, and a well-formed name that is not there is a 404. How the files are written and verified is in [Analytics](analytics.md#archives-and-backups).

`POST /analytics/cut` takes exactly one of `before_ms` (epoch milliseconds, not negative and not in the future) or `before_days` (1 to 36500, counted back from now). `archive` defaults to `true`: each UTC day older than the cutoff is written to a verified archive file and then deleted, oldest first, and a failure stops the run with 503 `{error}` after leaving the rows of the failing day in place. Only `"archive": false` deletes without a copy. `"dry_run": true` changes nothing and reports `rows` (rows older than the cutoff), `oldest_ms`, and an empty `files`. `files` lists the archive names written, `archived_rows` how many rows they hold. The cutoff is rounded down to a whole hour and the one used is returned as `cutoff_ms`. Bodies are limited to 1 MiB and unknown fields are a 400.

```sh
curl -H "Authorization: Bearer $TOKEN" -X POST https://node:7443/api/v1/analytics/cut \
  -d '{"before_days": 90, "dry_run": true}'
```

Backups, cuts (dry runs included), restores, downloads and deletes are recorded in the audit log as `analytics.backup`, `analytics.cut`, `analytics.restore`, `analytics.archive.download` and `analytics.archive.delete`. Turning off `store_client_ips` or `store_user_agents` in the settings also blanks the field in existing archives and backups, recorded as `analytics.archive.scrub` with the file counts. Downloads share the 2-at-once limit of exports and answer 429 beyond it.

`PUT /settings` takes `retention.hour_buckets_days` of 0 (keep forever, the default) or 1 to 3650, and `retention.archive_before_delete` (boolean, default `true`, which an older client may omit).

Analytics read failures return 500 `{error:"internal error"}`; the cause is in the connector log.

The `sizes` buckets are cumulative: `count` is the number of responses up to and including `le` bytes, and the final bucket (`le` null) equals the total, so clients subtract the previous bucket to draw a histogram.

## Dashboard server

The dashboard container exposes its own API under `/api/v1` for the browser. `/nodes` lists configured nodes, and `/nodes/{node}/...` proxies to the matching connector route above using the stored token. `POST /session` logs in to the dashboard (`{username,password,totp}`), `GET /nodes/summary` fans out `/node` across all nodes, and `POST /deployments` takes `{nodes:[name],site:Site,mode:"each"\|"replicate",per_node?,github_token?}` and applies the site to every selected node. In `each` mode, `per_node` maps a node name to `{blue?,green?}` target lists that replace the site's own for that node; `replicate` ignores it. `github_token` needs a site with a `source`.
