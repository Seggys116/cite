# Security model

This page covers node mode: who can reach what, which secrets exist and where they live, what the orchestrator overlay gives up, and what is out of scope. Single-site mode is covered by [Hardening](hardening.md) and the [Threat model](threat-model.md), and none of this page applies to it.

## Who can reach what

| Surface | Reachable from | Protection |
|---|---|---|
| HAProxy ports 80 and 443 | Anyone, on `CITE_PUBLIC_BIND` | Firewall rules, rate limit, body size limit |
| Connector API, port 7443 | Host IP in `CITE_CONNECTOR_BIND` | Allowlist, then TLS, then token |
| HAProxy admin socket `/run/cite/admin.sock` and master CLI `/run/cite/master.sock` | Processes that can open files in the `cite_run` volume: HAProxy and the connector only; no network listener | File ownership (uid 10001, directory mode 0750, socket mode 0600). See below. |
| Docker API through `cite-dockerproxy` | The connector, on the internal `docker_api` network | Deny-by-default filter on method, path, query and body |
| Site executors, port 8080 | HAProxy, over the stack's own internal network (or every container on `cite_edge` when per-stack networks are off) | Network isolation only |

### Connector API

A connection goes through these gates in order.

1. Allowlist. The connector checks the peer address straight after `accept`, before reading any TLS or HTTP bytes. An address outside `CITE_CONNECTOR_ALLOW` gets a closed connection and no response. The list is required, and an all-addresses entry such as `0.0.0.0/0` is refused unless the list also contains `allow-all`. The one exception is loopback, which is admitted for `/healthz` only so the container health check works whatever the list says.
2. TLS. On by default. The certificate comes from a per-node certificate authority generated by `init`: the CA is valid for 3650 days, and the server certificate for 825 days. The private keys are in `/conf/tls` (mode 0700, keys 0600). If you turn TLS off with `CITE_CONNECTOR_TLS=false`, the connector warns at start and expects a trusted tunnel.
3. Token. Every route except login and `/healthz` needs `Authorization: Bearer <token>`. A token is either a session token from login or a long-lived API token.

Other limits on the API: at most 256 simultaneous connections, 10 seconds to send headers and to complete a TLS handshake, 180 seconds per request, 15 minutes per connection, 32 KiB of headers and 1 MiB of request body. Responses carry `Cache-Control: no-store`.

### Login

Login needs the username, the password and a TOTP code, and all three are always checked so timing does not say which was wrong.

| Item | Detail |
|---|---|
| Password | Generated by `init`: 24 characters from a 57 character alphabet without look-alike characters. Stored as an Argon2id hash (19 MiB, 2 iterations). |
| TOTP | SHA-1, 6 digits, 30 second step, one step of drift either side. A code can be used once: the last accepted step is stored, and a failed password attempt does not use up a valid code. |
| Failed logins | 5 failures within 15 minutes lock that client for 30 seconds, doubling with each further failure up to 15 minutes. 100 failures from anyone within 5 minutes lock all logins for 60 seconds. The check and the failure count run one login at a time, so a burst of parallel attempts cannot exceed the limit. The response is 429 with `Retry-After`. The failure audit entry records the peer and whether the username matched, never the submitted username. |
| Sessions | 8 hours by default (`CITE_SESSION_TTL`, 60 seconds to 30 days), 30 minutes idle timeout, at most 1024 live sessions. A token is `cite_<id>.<secret>` with a random 64-hex secret; the secret is kept only in memory, never written to disk, and compared in constant time. They end when the connector restarts or when credentials are reset. |
| API tokens | `cite_<id>.<secret>`: a public 16-hex id and a 64-hex secret from the system random source. At most 64. Only an Argon2id hash of the secret is stored, with its own salt. The id selects the record, so malformed tokens and unknown ids are refused without hashing, and a secret that has already passed is remembered in memory until the token is revoked or the connector restarts. Each hash check for a known id is counted as a failure against the client address (IPv6 grouped by /64) before the hash runs, and the count is taken back only if the secret turns out to be right, so parallel or abandoned requests get no free guesses. After 5 failures that client is refused further hash checks for 30 seconds, doubling up to 15 minutes; tokens already verified keep working. At most 2 token hashes run at once, and a hash keeps its slot until it finishes even when the client disconnects. A token request abandoned mid-check (disconnect or timeout) stays counted as a failure by design and is not forgiven. Password logins use the same /64 grouping and the same rule: the attempt is counted (including toward the global ceiling) before the password hash runs and taken back only if the login succeeds, so a login abandoned mid-check still counts, and only one password hash runs at a time. Resetting credentials revokes them all, including in a running connector. Only a login session can create, list or revoke API tokens; an API token gets 403 on those routes. |

Configuration changes are recorded in the audit log with the actor. API tokens appear as `api:<name>`.

### Dashboard

The browser signs in to the dashboard with its own username, password and TOTP code, then the dashboard server calls each connector with a stored connector API token. The dashboard is therefore a holder of one token per node. Anyone who gets into the dashboard, or who reads its stored tokens, can act on every node it manages, within the API's limits. Restrict each connector's allowlist to the dashboard's address, and keep the dashboard on an address you control.

Until an account exists the dashboard prints a one-time setup token to its log on every start, and the setup form needs it, so nobody who can merely reach the port can claim the console. It is published on `127.0.0.1` by default. The session cookie is `__Host-cite_session` with `Path=/` and no `Domain` when it is Secure (TLS, or `CITE_DASHBOARD_COOKIE_SECURE=true`), and a request carrying two cookies with that name counts as signed out. Dashboard sign-ins are rate limited per client address, with a dashboard-wide lockout that only attempts naming the real account count toward. Running `init --force` or a connector credential reset takes effect in the running process, which signs everyone out. [Dashboard](dashboard.md#signing-in) has the details. The [desktop app](desktop.md) keeps the same kind of token for each node in the operating system keychain instead.

## Secrets at rest

All state is in the `cite_conf` volume, described in [Running a node](node.md#what-is-stored).

| Secret | File | Form |
|---|---|---|
| Login password | `credentials.json` | Argon2id hash |
| TOTP secret | `credentials.json` | Plain base32 key, needed to verify codes |
| API tokens | `tokens.json` | Argon2id hashes |
| GitHub tokens | `secrets.json` | Plain text, up to 512 entries of 16 KiB |
| TLS CA and server keys | `tls/` | PEM files |

Files are written atomically with mode 0600.

HAProxy and the connector both run as uid 10001, so file modes alone would not keep HAProxy out of the connector's files. The separation comes from the mounts: HAProxy mounts only the `haproxy` and `certs` subpaths of `cite_conf`, read-only, so `credentials.json`, `tokens.json`, `secrets.json` and the TLS keys under `/conf/tls` are not visible inside the HAProxy container. The two containers also do not share a process namespace, so a compromised HAProxy cannot read the connector's memory or `/proc` entries, or signal it. Site certificates for HAProxy in `/conf/certs` are visible to HAProxy by design.

The credential report from `init` is printed once and not stored. The debug output for credentials and for the report hides the password, the hash and the TOTP secret.

## The HAProxy admin sockets

HAProxy exposes two admin-level control sockets with no authentication: the admin socket (`stats socket`), which the connector uses to switch slots, toggle maintenance and read backend health, and the master CLI (`-S`), which the connector uses to reload. Both are unix sockets in the `cite_run` volume, so there is no TCP listener to reach from any network, and a site target pointing at an HAProxy address cannot hit them.

The volume is mounted only in the HAProxy and connector containers, which both run as uid 10001. Site executors, which run the site's own server code, are on their own per-stack networks (or `cite_edge`) and cannot see the volume. HAProxy is the internet-facing process, so a compromised HAProxy can reach its own sockets, which it owns anyway. The log sink is a unix datagram socket (mode 0600) and only parses datagrams. The connector API still applies its allowlist.

The master CLI address in the compose `command` and `CITE_HAPROXY_MASTER` must be kept in step. Reloading no longer needs signals or a shared process namespace.

## Config injection

The connector builds `haproxy.cfg` from JSON that clients send, so every value is checked before it can reach the file.

- Ids are limited to `[a-z0-9-]`, 40 characters, starting with a letter or digit.
- Hosts must be valid host names, optionally with a leading `*.`.
- Patterns and path prefixes are limited to printable ASCII without `#`, `"`, `'`, `$name`, a leading `-`, or HAProxy keywords like `if`, `or`, `{` and `}`. Regexes must compile.
- Targets must be `host:port` or `[ipv6]:port`, and may not name loopback, link-local, unspecified or multicast addresses, `localhost`, the stack's own service names, or odd IPv4 spellings. See [Firewall and maintenance](firewall.md#targets-and-health-checks).
- Firewall rules match both the normalised path and a canonical form with path parameters, backslashes and encoding removed, so encoded or `;`-decorated paths do not slip past a rule.
- Render options (directories and addresses) accept only letters, digits and `/ . _ -` plus `@ : [ ]` for addresses.
- Maintenance pages are written to separate files and never placed in the config, and are limited to 15000 bytes. The built-in page makes no external requests.
- The result is checked with `haproxy -c` on a staged copy before the live file is replaced, and a rejected change restores the previous stored configuration.

Tests render hostile hosts, regexes and ids and check that no extra directive lines appear.

## The firewall's limits

The firewall removes known probe traffic. It does not replace a web application firewall: it matches path, method, user agent, source address and host, and nothing in bodies or cookies. Source addresses are the TCP peer, so behind another proxy they are the proxy's address. The rate limit is per node. The `(?i)` flag in the presets needs a PCRE-enabled HAProxy. See [Firewall and maintenance](firewall.md).

## The orchestrator overlay

Single-site mode never mounts the Docker socket. That is a design rule, and the overlay breaks it on purpose so one connector can create site stacks. The overlay is built so that a compromised connector gains far less than the daemon's full power.

What the overlay adds:

- A `dockerproxy` container (`cite-dockerproxy`) is the only one with `/var/run/docker.sock`. The connector reaches it over the internal `docker_api` network at `http://dockerproxy:2375`. The socket bind is marked read-only, which does not restrict the API; the filter does.
- The proxy forwards only the calls the orchestrator makes and rebuilds the expected body for each container, volume and network create, rejecting anything that differs. See [Orchestrator](orchestrator.md#the-docker-proxy) for the full list.
- The proxy runs as uid 10001 with the socket's group added, a read-only root filesystem, no capabilities, `no-new-privileges`, and memory, CPU and pids limits.

Replaced: earlier versions put a generic socket proxy (`tecnativa/docker-socket-proxy`) here. Such proxies allow or deny whole API sections by path. With containers and POST enabled, a client may create a container with `Privileged`, a `/:/host` bind, host PID or network mode, all capabilities or raw devices, and then start it, which is root on the host. With volumes enabled, a local volume with bind options mounts the host's root. With images enabled, any image from any registry can be pulled. With networks enabled, any container can be attached to the control network. `cite-dockerproxy` blocks each of these because it checks the body, not just the path. It also rejects JSON with duplicate keys and forwards a re-encoded copy of the body it validated.

What the connector can still do through the proxy: create, start, stop and remove containers named `cite-<id>-<slot>-<role>` from Cite images in the configured registry with the fixed hardened specification, create and delete the matching `cite.managed` volumes and networks, and attach the HAProxy container to the per-stack networks. It cannot exec into or attach to a container, read logs, copy files, pull other images, bind host paths, use host namespaces, add capabilities, or touch a container, volume or network that lacks the `cite.managed=true` label.

Site isolation: every stack has its own internal network that only its executor and HAProxy join, so one site's code cannot reach another site's executor, the connector, or HAProxy's admin sockets. If `CITE_HAPROXY_CONTAINER` is set empty, executors share `cite_edge` and can reach each other. That is a weaker mode, for nodes whose sites are all trusted.

Residual risks:

- The Docker socket is still the proxy's own privilege. A compromised proxy process, or anyone who can reach the socket from the host, has root on the host. The proxy is small, has no shell and no write access to its own filesystem, but it is the one component whose compromise is total.
- The filter is only as strict as its tests. The proxy ships tests that feed every specification the orchestrator can emit through the validator and a set of hostile variants through the HTTP layer, so a change to the orchestrator that the proxy does not accept fails the build.
- GitHub tokens sit in `secrets.json` and in the manager container's environment, readable by anyone who can inspect containers. The proxy allows inspecting stack containers, so a compromised connector can read the tokens it already holds.
- Anything that lets someone act through the connector (its API tokens, its sessions, a bypass of the allowlist) can still create, stop and delete stacks, and so can disrupt or replace sites on the node, though it cannot reach the host through Docker.
- Disk is not limited per stack. Docker's per-container storage quota and volume driver options are blocked by the proxy, so a site whose build fills its volumes can fill the host disk. Use an XFS data root with project quotas, or monitor disk use.
- Images are trusted by tag from the configured registry. A compromised registry account or a moved tag changes what runs. Pin the registry to one you control.
- Containers share the host kernel. A kernel or runtime escape from a site stack is out of scope, as it is in single-site mode.

If you do not need GitHub builds on the node, leave the overlay off and give sites upstream addresses. The connector then has no Docker access at all.

## Out of scope

- Compromise of the Docker host, kernel or Docker daemon.
- A malicious or compromised site build. Builds run in the manager as an unprivileged user with an egress-only network, and executors have no shell, but this does not make untrusted code safe.
- Denial of service from volume. The rate limit and connection cap shed load; they do not stop a flood at the network level.
- Protection of traffic between HAProxy and site targets. Targets are plain `host:port` over HTTP.
- Multiple users or roles. A connector has one login and up to 64 equal API tokens.
- Listing or revoking other sessions. A session ends by timeout, by logout of that session or by restarting the connector.
- Public HTTPS certificate issuance. HAProxy loads certificates you place in `/conf/certs`.
